## 数据治理规则

1. `data/raw` 中的文件不重命名内容、不覆盖、不手工修改。
2. 每次解析均记录源文件哈希，证据通过哈希、页码和坐标回链。
3. `data/interim` 和 `artifacts` 可由流水线重建，不作为事实来源。
4. 模型训练只读取 `data/processed`，禁止直接从报告或上市后材料取特征。
5. 测试样本必须是可公开或已脱敏的小文件，官方数据不进入Git。
6. 赛事整包先由 `scripts/check_competition_data.py` 检查，再由
   `scripts/import_competition_data.py` 标准化；禁止直接用截断主表或上市后行情构造上市前特征。

每家公司在三个类型目录中使用完全相同的子目录名，例如：

```text
data/raw/prospectus/03696_英矽智能/
data/raw/company_info/03696_英矽智能/
data/raw/market/03696_英矽智能/
```

`company_info/<公司目录>/公司信息.json` 是三类原始文件的关联入口。每家公司在 `raw` 主数据区只保留两个 JSON：公司信息和日线行情；供应商快照及交叉核验材料进入 `data/interim/audit`。

所有PDF和结构化数据均先登记到 `data/app.db`。PDF解析、向量和截图路径必须包含
稳定的 `document_id`，禁止只按公司目录写出，以免多份资料互相覆盖。详细操作见
`docs/资料登记与版本管理.md`。

语义索引按 `document_id/embedding_model` 隔离。正式RAG查询使用PostgreSQL + pgvector；
`vectors.npy`、`metadata.json` 和 `manifest.json` 作为本地可恢复缓存保留。专业Agent先根据
角色职责和风险定义自主生成语义问题，再用这些问题查询当前文档的向量索引；搜索规划或
向量接口失败时，固定多查询BM25才作为兜底向DeepSeek提供候选。
文字层表格另存到 `data/interim/tables/<公司>/<document_id>/tables.jsonl`，并生成带多层
表头、单位、期间、Markdown、逐行语义及单元格来源的 `chunk_kind=table` 切片；该切片与
普通文本使用同一Embedding模型和检索器，不建立割裂的第二套知识库。
风险发现Agent先分批扫描全文，开放风险只能引用当前批次真实 `chunk_id`；随后由独立的大模型
节点从全文视角合并语义重复项，每条原始候选必须留下唯一去向。固定目录不参与批次主题发现，
只用于全局合并后的重合标记和失败批次兜底。全文发现与公司适用性判断完成后先等待人工确认
风险范围，人工可查看候选漏斗、取舍、改派、补充要求或新增方向，随后四个专业Agent才会并行
启动。DeepSeek只能选择本次候选 `chunk_id`；
模型重试耗尽后，分析引擎才回退到满足全部锚定
关键词的BM25规则结果，并把实际问题、尝试次数和原因写入AgentTrace。

财务、法务、业务和市场Agent的结果提交给决策Agent。决策Agent只能引用专业Agent已选中的
提案和证据，接受、调整、驳回及分歧都会记录在父子AgentTrace中。Embedding以批次为重试
单位；专业分析和决策均以完整的调用、JSON解析和白名单校验为重试单位。
