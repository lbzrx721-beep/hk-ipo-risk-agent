# 核心数据契约

当前契约版本为 `1.0`。代码唯一权威定义位于 `src/ipo_risk/domain/models.py` 和
`src/ipo_risk/domain/enums.py`；资料目录契约位于 `src/ipo_risk/domain/catalog.py`。
本文档负责解释字段和跨对象业务规则。

## 全局约定

1. 所有主对象必须包含 `schema_version="1.0"`，未知字段直接拒绝。
2. `source_hash` 是源文件哈希的唯一字段名，值为小写 SHA-256；不再使用 `source_file_hash`。
3. `status` 是风险核验状态的唯一字段名；不再使用 `verification_status`。
4. `page` 是从 1 开始的 PDF 物理页序号，也是定位、截图和回链的唯一页码主键。
5. `printed_page_label` 是页面底部印刷的页码标签，例如 `222`、`I-22`；它仅用于展示，可以为空。
6. `bbox=[x0,y0,x1,y1]` 使用 PDF 页面坐标，必须满足 `x0 < x1`、`y0 < y1`。
7. 置信度和概率统一使用 `[0,1]` 区间的小数。
8. 日期使用 `YYYY-MM-DD`；时间使用带时区的 ISO 8601 格式。
9. 对象之间通过稳定 ID 引用，不复制另一对象的完整内容。

## 资料目录契约

- `CompanyRecord`：公司统一编号、标准目录、上市日期和 `公司信息.json` 哈希。
- `DocumentRecord`：一份不可变资料版本；必须包含类型、文件、SHA-256、文档日期和
  `available_at`。
- `DatasetRecord`：一份结构化数据快照；必须区分数据期间、实际可用日期和
  `pre_listing_eligible`。
- `VectorIndexRecord`：一个 `document_id` 在指定Embedding模型和维度下的索引登记。

文档ID由“公司＋逻辑类型＋文档日期＋哈希前8位”生成，例如：

```text
doc_03696_prospectus_2025-12-18_c44e3c20
```

映射键只是资料清单内的唯一名称；同一类型有多个版本时，可使用
`prospectus_main`、`prospectus_supplement` 等不同键，并统一填写
`document_type="prospectus"`。SQLite结构的唯一权威定义为
`src/ipo_risk/storage/schema.sql`。

## Evidence

`Evidence` 是一条能够重新定位到原始 PDF 的事实证据。原文必须保持官方语言，简体中文只能作为派生展示文本。

必填字段：

- `evidence_id`：证据唯一 ID。
- `company_id`：公司统一编号。
- `document_id`：招股章程、配发公告等文档版本 ID。
- `source_file`、`source_hash`：源文件路径和 SHA-256。
- `page`、`bbox`、`quote`：PDF 页、页面坐标和必要长度的原文。
- `evidence_type`：`text`、`table`、`ocr_text` 或 `image`。
- `extractor`：生成证据的标准 Agent 角色。
- `confidence`：证据定位置信度。
- `available_at`：该证据对预测系统可用的日期。
- `created_at`：对象生成时间。

`printed_page_label` 和 `screenshot_path` 均为可选字段。印刷页码可能缺失、重复或按附录重新编号，因此不能替代物理页码；页码和坐标必须始终存在，以便截图可以重建。
当 `evidence_type=table` 时，必须同时保存 `table_id`，并以等长的
`table_cell_refs/table_cell_values` 记录当前表格切片覆盖的单元格来源和值。模型阅读的是
结构化Markdown与逐行语义，确定性核验使用这些单元格引用回查原始PDF坐标。

```json
{
  "schema_version": "1.0",
  "evidence_id": "E0001",
  "company_id": "03696",
  "document_id": "prospectus_2025-12-18",
  "source_file": "data/raw/prospectus/03696_英矽智能/招股章程_2025-12-18_繁体中文.pdf",
  "source_hash": "c44e3c20c02747bb8768eefedd8703ff841b242d1b8cb96adc50b18b5a51809b",
  "page": 231,
  "printed_page_label": "222",
  "bbox": [72.0, 146.0, 518.0, 314.0],
  "quote": "招股书原文切片",
  "evidence_type": "text",
  "extractor": "finance",
  "confidence": 0.91,
  "available_at": "2025-12-18",
  "screenshot_path": "artifacts/evidence/03696/E0001.png",
  "created_at": "2026-07-17T06:00:00+00:00"
}
```

## RiskFinding

`RiskFinding` 是一条风险判断，只通过 `evidence_ids` 引用 Evidence，不能把原文和风险结论混成一个对象。

必填字段：`finding_id`、`company_id`、`risk_type`、`title`、`severity`、`claim`、
`evidence_ids`、`status`、`confidence`、`created_by`、`created_at`。

`status` 只能是 `proposed`、`pending_verification`、`verified` 或 `rejected`。只有派生计算
结论使用 `calculation` 保存工具名、公式、输入、结果、单位、期间及每个输入的
`source_refs`；招股书直接披露的年份、金额和比例通过Evidence原文引用核验，不要求伪造公式。
`uncertainty` 保存仍未消除的不确定性。

```json
{
  "schema_version": "1.0",
  "finding_id": "F0001",
  "company_id": "03696",
  "risk_type": "cash_burn",
  "title": "现金覆盖期偏短",
  "severity": "high",
  "claim": "按已披露期间的现金消耗速度，现有资金覆盖期存在压力。",
  "evidence_ids": ["E0001", "E0002"],
  "status": "verified",
  "confidence": 0.88,
  "created_by": "finance",
  "calculation": {
    "tool": "calculate_cash_runway",
    "formula": "cash_balance / annual_cash_burn * 12",
    "inputs": {"cash_balance": 100.0, "annual_cash_burn": 80.0},
    "result": 15.0,
    "unit": "month",
    "period": "FY2025",
    "source_refs": {
      "cash_balance": "company_info:financials.cash_balance",
      "annual_cash_burn": "company_info:financials.annual_cash_burn"
    }
  },
  "uncertainty": null,
  "created_at": "2026-07-17T06:00:01+00:00"
}
```

## AgentTrace

`AgentTrace` 是一个 Agent 节点的完整执行记录。它记录角色、输入引用、确定性工具调用、输出引用、结果状态和裁决理由。

必填字段：`trace_id`、`run_id`、`agent`、`started_at`、`ended_at`、`input_refs`、
`tool_calls`、`output_refs`、`status`、`decision`。子节点可通过 `parent_trace_id` 关联父节点。

```json
{
  "schema_version": "1.0",
  "trace_id": "T0001",
  "run_id": "RUN_03696_001",
  "parent_trace_id": null,
  "agent": "finance",
  "started_at": "2026-07-17T06:00:00+00:00",
  "ended_at": "2026-07-17T06:00:02+00:00",
  "input_refs": ["E0001", "E0002"],
  "tool_calls": [],
  "output_refs": ["F0001"],
  "status": "succeeded",
  "decision": "提交证据核验 Agent 复核",
  "error": null
}
```

失败的工具调用或 AgentTrace 必须填写 `error`；`ended_at` 不得早于 `started_at`。
所有真实模型工具调用还必须在 `output` 中保存 `prompt_version`、`prompt_sha256` 和
`prompt_snapshot`。结构或证据校验触发纠错重试时，`repair_errors` 保存每次被拒绝的原因；
由此可以把历史输出精确对应到当时实际发送的提示词，而不是只依赖可能变化的文件名。

多角色分析与裁决使用以下可审计工具调用：

- `open_risk_discovery`：位于风险发现子轨迹中，记录全文切片数、提示词版本、章节包数、包内
  原始候选数、完整原始候选、实际尝试次数和失败批次；同时记录全局语义合并后的风险、
  每条原始候选到合并风险的唯一映射、目录重合与补入数量、种子证据 `chunk_id`、合并尝试
  次数及降级原因。首轮要求完整发现，只有仍存在证据独立的重大遗漏时允许一次 `has_more`
  补扫；请求容量限制章节包大小，不得限制公司风险总数。发现提示词不得接收固定目录主题，
  固定目录只允许在全文候选形成后
  用于语义重合标记和失败批次兜底。
- `agent_search_planning`：记录专业Agent职责、风险类型、模型自主生成的实际语义问题、
  提示词版本、尝试次数，以及固定查询兜底原因。
- `evidence_retrieval`：记录BM25/混合模式、Embedding模型、候选chunk、融合分数、词法与
  语义分数及各自排名，并记录Embedding请求与重试次数；向量失败时记录 `fallback_error`。
- `evidence_analysis`：记录规则ID、候选chunk白名单、角色内批次、专业状态、选中chunk、
  严重程度、置信度、补证问题、`attempts`与`retries`；状态只能为支持、需补证、证据不足、
  主体或期间错配、重复合并或冲突，不允许机器写最终驳回。
- `grounded_risk_analysis`：位于财务、法务、业务或市场子轨迹中，汇总该角色一条规则的
  多查询检索模式、候选和选中证据、模型模式、尝试次数及失败原因。
- `risk_adjudication`：位于决策子轨迹中，记录完整提案账本、全量裁决批次、模型与提示词
  版本、尝试次数、降级兜底、冲突清单和最终进入人工复核的风险类型。

DeepSeek输出只能引用本次候选白名单中的 `chunk_id`。未知、重复、超出规则数量上限的证据
引用均视为无效输出，不能生成RiskFinding。模型生成的风险仍统一进入
`pending_verification`，不得绕过确定性核验和人工复核。

全局合并必须完整覆盖所有批次原始候选：每个 `candidate_id` 必须且只能映射一次；合并风险
引用的证据必须来自其来源候选。人工范围确认之前不得按固定风险数量静默截断。全局模型重试
耗尽时允许按同角色完全相同标题合并，但必须保留全部不同候选并记录降级错误。

`open_*` 开放风险必须由专业证据模型标记为 `supported` 且引用有效原文，才能进入决策Agent。
决策Agent逐项复核全部有证据提案；模型失败或对已支持风险返回 `accepted=false` 时，系统
保留专业提案、记录冲突并交给人工，而不是静默删除。证据不足项不会生成正式RiskFinding，
但必须保留在提案账本和 AgentTrace 中。

决策模型受双重白名单约束：`source_proposal_ids` 必须来自本次角色子节点，
`evidence_chunk_ids` 必须属于这些提案已经选中的证据。总控、角色与决策轨迹通过
`parent_trace_id` 形成父子关系；复核界面从候选报告读取并展示这些不可变轨迹。

## EvidenceVerification 与 FindingVerification

`EvidenceVerification` 保存对一条Evidence的可复现核验快照。检查项至少覆盖源文件存在性、
SHA-256、PDF物理页、坐标和原文；声明了 `screenshot_path` 时还必须检查截图存在。

`FindingVerification` 汇总RiskFinding的证据引用、公司归属、全部Evidence核验以及数值公式
复算结果。含数字的 `claim` 必须提供 `Calculation`；公式只允许数字、已声明输入、括号和
加减乘除，禁止函数调用、属性访问和任意代码执行。规则中的字段路径负责从结构化公司资料
解析输入，`source_refs` 必须覆盖全部输入。只有全部检查通过时 `passed=true`。

## FindingReview

`FindingReview` 是一次不可变的人工复核审计记录，包含：

- `review_id`、`run_id`、`finding_id`：复核与分析任务定位。
- `decision`：`confirmed`、`rejected` 或 `edited`。
- `reviewer`、`comment`、`created_at`：复核责任人与意见。
- `verification`：作出决定时使用的完整确定性核验快照。
- `resulting_finding`：决定生效后的完整RiskFinding。

`confirmed` 和 `edited` 只有在 `verification.passed=true` 时才能生成
`status=verified`；`rejected` 允许保存失败核验并生成 `status=rejected`。
`rejected` 和 `edited` 必须填写意见。复核记录与RiskFinding状态在同一个SQLite事务中写入，
后续重新保存候选报告不得把 `verified` 或 `rejected` 状态降回待核验。

## Prediction

`Prediction` 表示一家公司在一个交易日时间窗上的风险概率。1、5、20、60 日分别生成独立对象。

必填字段：`prediction_id`、`company_id`、`as_of_date`、`horizon`、`target`、
`risk_probability`、`risk_level`、`model_version`、`feature_snapshot`、`explanations`、`created_at`。

每个特征都必须使用 `FeatureValue` 同时记录 `value`、`available_at` 和 `source_ref`。代码会拒绝
任何 `available_at > as_of_date` 的特征，从数据结构层面阻止上市后信息泄漏。

```json
{
  "schema_version": "1.0",
  "prediction_id": "P0001",
  "company_id": "03696",
  "as_of_date": "2025-12-29",
  "horizon": 5,
  "target": "significant_drop",
  "risk_probability": 0.67,
  "risk_level": "high",
  "model_version": "baseline_v1",
  "feature_snapshot": {
    "cornerstone_ratio": {
      "value": 0.3929,
      "available_at": "2025-12-29",
      "source_ref": "company_info:offering.cornerstone_ratio_of_offer"
    }
  },
  "explanations": ["基石投资者占发售股份比例为39.29%"],
  "created_at": "2026-07-17T06:00:03+00:00"
}
```

## 跨对象验收规则

1. Evidence 的 `source_hash` 必须与实际源 PDF 一致，页码与坐标能够重新截图。
2. RiskFinding 引用的全部 `evidence_ids` 必须存在且属于同一公司。
3. 只有 `status=verified` 且至少引用一条有效 Evidence 的 RiskFinding 可以进入最终报告。
4. AgentTrace 的 `input_refs`、`output_refs` 和 ToolCall 必须能够回到实际对象或产物。
5. Prediction 的所有特征必须在 `as_of_date` 当日或之前可用。
6. API、存储、Agent、报告和界面只能导入 `ipo_risk.domain` 中的定义，不得各自复制模型。
7. 最终报告只能在全部RiskFinding进入终态后导出，且只能包含 `status=verified` 的风险及其证据。
